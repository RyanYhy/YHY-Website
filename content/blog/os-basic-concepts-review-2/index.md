10 月 20 日这次整理的重点是处理机调度。[上一篇](/blog/os-basic-concepts-review/)主要在区分程序、作业、进程，以及并发、同步这些概念；这一篇接着看：有多个任务需要运行时，系统怎样决定谁先用 CPU、用多久，以及什么时候换人。

我先把调度分成几个层次，再看衡量调度效果的指标，最后比较不同算法。这样看下来，算法之间的区别就不只是名字不同，而是在回答不同的问题：是让任务尽快做完，让用户尽快得到响应，还是先保证截止时间？

## 处理机调度的三个层次 {#scheduling-levels}

我第一遍记这三个层次时，主要抓它们分别在决定什么。

**高级调度，也叫作业调度，决定接纳哪些作业。** 在传统批处理模型中，系统从外存后备队列里选择合适的作业，将它们装入内存、建立进程，让它们有资格参与后续运行。它控制的是进入系统参与竞争的作业数量和组合。

**中级调度，也叫内存调度，决定哪些进程暂时挂起、哪些可以调回内存。** 内存紧张时，可以把暂时不运行的进程换出，之后再调入。它关注的是已接纳进程的驻留与挂起，不是每次选谁上 CPU。

**低级调度，也叫进程调度或短程调度，从就绪进程中选出下一位运行者。** 后面讨论的 FCFS、时间片轮转等规则，主要是在这个层次上理解。

我先把它们记成：**先决定谁能进来，再决定谁暂时留在内存，最后决定谁现在运行。** 这是教材里的分层模型，不要求每个实际系统都有三套独立调度器。

### 多道批处理为什么需要调度 {#multiprogramming}

批处理强调的是：用户先提交作业，由系统组织执行，运行过程中通常不需要持续交互。

“多道”则意味着内存中可以同时容纳多个作业对应的进程。当一个进程等待 I/O 时，CPU 可以转去执行其他就绪进程，减少空闲时间。

因此，多道批处理不是“多个作业同时占着一个 CPU 执行”，而是让多个作业共同参与资源使用，在适当的时候切换运行者。这里的目标是提高系统资源利用率，不只是把队列排起来。

## 抢占与非抢占的区别 {#preemption}

我觉得这里最本质的区别是：**一个进程本来还能继续执行时，系统能不能主动把 CPU 收回来，交给其他进程。**

非抢占式调度中，进程获得 CPU 后，通常要等它完成，或者主动因 I/O、等待事件等原因放弃 CPU，系统才选择其他进程。

抢占式调度则允许系统在它仍可运行时切换出去，例如时间片用完，或者出现了更高优先级的就绪进程。

这里要分清“重新调度”和“抢占”。当前进程已经结束，系统选择下一个进程，这是重新调度，但没有把一个仍在运行的进程赶下 CPU。这个区别在理解最短剩余时间算法时也会用到。

## 调度效果怎样衡量 {#metrics}

在比较算法前，我先把几个指标分开。周转时间短、CPU 很忙、完成的任务多，并不是同一个意思。

### 周转时间与平均周转时间 {#turnaround}

**周转时间 = 完成时刻 - 提交或到达时刻。**

它衡量的是一个作业从提交到最终完成，一共经历了多久。中间等待 CPU、实际执行、等待 I/O 等时间，都可能包含在里面。

**平均周转时间 = 所有作业周转时间之和 / 作业数。**

它描述一批作业平均多久完成。CPU 利用率则看某段观察时间内，CPU 有多少比例的时间在忙碌；吞吐量看单位时间完成多少个任务。这三个指标需要分别看。

### 带权周转时间 {#weighted-turnaround}

只看周转时间，还不容易比较长短不同的作业。我用带权周转时间看总耗时相对于自身服务需求放大了多少：

```text
带权周转时间 = 周转时间 / 服务时间
```

在忽略 I/O 和切换开销、每个任务只有一段 CPU 执行的简单模型中，服务时间就是所需的 CPU 时间，此时可以进一步写成：

```text
周转时间 = 等待时间 + 服务时间
带权周转时间 = (等待时间 + 服务时间) / 服务时间
             = 1 + 等待时间 / 服务时间
```

括号不能省掉，否则“等待时间 + 服务时间 / 服务时间”会变成另一个式子。实际过程包含 I/O 等额外耗时时，也不能只用就绪队列等待时间和 CPU 执行时间解释全部周转时间。

比如同样经过 10 个时间单位完成，一个只需运行 2 个单位的作业，带权周转时间是 5；一个需要运行 10 个单位的作业，带权周转时间是 1。前者相对于自身的执行需求，经历了更多额外耗时。

服务时间为正时，这个比值通常不小于 1。在 CPU 初始空闲、作业到达后立即运行，且没有 I/O 等额外耗时的简单模型中，第一个作业的比值为 1。不能只凭“非抢占”就认定第一个作业一定满足这些条件。

### 不同系统的侧重点 {#system-goals}

**批处理系统** 主要关注平均周转时间、吞吐量和 CPU 利用率。作业最好尽快完成，单位时间能处理更多任务，资源也不要长期空闲。

**分时系统** 更关注交互响应。多个用户发出操作后，都应该比较快地得到响应，而且不希望体验忽快忽慢。响应快不等于整个任务马上完成，任务可以先得到处理机会，再继续运行。

**实时系统** 的核心是满足时间约束。重要的不只是平均速度快，而是关键任务能否在截止时间前完成，以及这种行为是否可预测。

所以，评价一个算法前，先要知道系统更关心什么。一个平均周转时间较短的方案，不一定能提供最好的交互响应。

## 常见调度算法 {#algorithms}

下面先按教材中的简化模型理解：讨论单个处理机的调度，执行时间用来表示作业或当前 CPU 执行段的服务需求。实际系统通常需要估计执行时间，而不是提前知道进程将来要运行多久。

### 先来先服务：FCFS {#fcfs}

FCFS 是 First-Come, First-Served，核心就是按到达顺序排队。就绪队列中的新进程进入队尾，调度时从队首选择。

它通常是非抢占式的，也可以用于作业调度。实现简单，已经排在前面的任务不会被后来的任务反复插队。

但排队公平不代表等待很短。如果一个很长的任务先运行，后面很短的任务也只能等着。在前面的任务最终会让出 CPU 的通常模型下，FCFS 不会因为持续有新任务到来，就让某个已入队任务无限期推迟。

### 短作业或短进程优先：SJF / SPF {#sjf}

SJF 是 Shortest Job First，SPF 常指 Shortest Process First。它们优先考虑服务时间较短的任务；用于进程调度时，通常关注下一段 CPU 执行的预计长度，而不是进程整个生命周期。

非抢占式版本在 CPU 可重新分配时，从已经到达、可以参与竞争的任务里选最短的。

抢占式版本通常称为 **最短剩余时间优先，SRTF**。此时比较的是剩余执行时间：新进程进入就绪队列后，如果它需要的时间比当前进程剩下的还短，就可能抢占 CPU。当前进程完成后也要重新选择，但那不算抢占。

这类算法对短任务有利，却可能让长任务饥饿：如果更短的任务持续到来，长任务就可能一直被排在后面。

### 高响应比优先：HRRN {#hrrn}

HRRN 是 Highest Response Ratio Next。它既考虑任务有多短，也考虑已经等了多久：

```text
响应比 R = (已经等待的时间 W + 预计服务时间 S) / S
         = 1 + W / S
```

每次需要选择任务时，从候选任务中挑响应比最大的一个，通常采用非抢占方式。

它与单纯的短作业优先相比，多考虑了等待时间。服务时间相同时，等得更久的任务更优先；等待时间相同时，较短任务的响应比更大。

例如，假设任务 A 已等待 6 个单位，预计还需要服务 3 个单位，它的响应比是 3；任务 B 已等待 2 个单位，预计需要服务 1 个单位，响应比也是 3。两者相同时，再按题目约定处理平局。

这里的响应比是在任务尚未完成时，用当前等待时间和预计服务时间算出的选择依据，**不是已经完成后统计出来的实际周转时间**。它通过等待越久、优先级越高的方式，缓解长任务在 SJF 中长期得不到服务的问题。

### 时间片轮转：RR {#round-robin}

RR 是 Round Robin。系统将 CPU 时间分成一段段时间片，让就绪队列中的进程依次运行。

一个进程用完时间片后，如果还没有完成、也没有阻塞，就回到队尾等待下一轮。如果它提前结束，或者因 I/O 等原因阻塞，就提前让出 CPU；阻塞的进程应进入相应的等待队列，而不是继续在就绪队列里轮转。

这是一种抢占式调度。只要队列中的任务都能按有限时间片轮流推进，新到来的任务又按规则进入队尾，就不会因为一直被插队而饥饿。

时间片太大时，许多任务在一轮内就完成，RR 会接近 FCFS。时间片太小时，响应机会更频繁，但调度和上下文切换也更频繁。这里的开销主要包括保存、恢复执行现场，以及可能的缓存影响，不能只理解成切换 PCB 或 JCB。

### 多级队列调度 {#multilevel-queue}

多级队列先把就绪进程分到不同队列，不同队列可以有不同优先级，也可以采用不同算法。例如，前台交互任务采用时间片轮转，后台批处理任务采用 FCFS。

需要同时看两套规则：**队列内部怎样选，队列之间怎样分配 CPU。**

队列之间既可以采用严格优先级，也可以按一定比例分配时间。是否允许高优先级队列抢占低优先级队列，也需要明确。

传统多级队列通常按进程类别固定分组，进程不随运行表现自由改变队列。“系统进程优先于用户进程”“前台优先于后台”可以是一种策略，但不是所有系统都必须遵守的固定顺序。

### 多级反馈队列：MLFQ {#mlfq}

多级反馈队列与多级队列最关键的区别，在于进程可以根据运行表现改变所属队列和优先级。

我先按一种常见的教材模型理解：

1. 设置多个不同优先级的就绪队列，新进程先进入高优先级队列。
2. 高优先级队列先运行，同级进程按时间片轮转；常见设计中，优先级越低，时间片越长。
3. 进程用完该级分配的时间额度仍未完成，就降到下一级队尾；已经在最低级时，则继续在本级轮转。
4. 高优先级队列出现新的就绪进程时，可以抢占正在低优先级队列运行的进程。被抢占进程怎样重新入队、剩余额度怎样计算，要看具体规则。

这里“队列按先后次序取进程”不等于该队列采用非抢占 FCFS。只要规定了时间片到期就轮到下一位，同级就体现的是时间片轮转。

“反馈”指的是：系统观察进程的 CPU 使用行为，再调整后续调度。用完一轮额度还没完成，是调整优先级的一种依据；具体实现还可以考虑提前阻塞、累计使用额度和优先级提升等规则。

```text
观察运行表现 -> 调整优先级 -> 再次调度 -> 继续观察
```

它不需要事先准确知道每个任务要运行多久。新任务有机会很快得到处理，短任务可能在较高优先级就完成，长任务则逐渐进入更适合持续运行的队列。

但如果高优先级任务一直不断，低优先级任务仍可能饥饿。可以通过老化、周期性提升优先级等机制改善，因此“是否饥饿”还要看有没有这些保护规则。

## 用同一组任务比较三种选择 {#worked-example}

为了把前面的取舍放在一起看，我用一个简化的假设：A、B 都在时刻 0 到达，入队时 A 在 B 前面；A 需要 8 个时间单位，B 需要 2 个。忽略 I/O 和上下文切换开销。

**FCFS** 先让 A 做完，再执行 B：

```text
0        8    10
|   A    | B  |
```

A 的周转时间是 8，B 是 10，平均周转时间为 9。B 要到时刻 8 才第一次获得 CPU。

**非抢占 SJF** 先做较短的 B，再做 A。B 在时刻 2 完成，A 在时刻 10 完成，平均周转时间为 6。它让短任务尽快结束，但前提是这里能知道或估计两者的服务时间。

**RR** 如果时间片为 2，则先运行 A 两个单位，再运行 B。B 在时刻 4 完成，之后只剩 A，就继续运行到时刻 10。两者平均周转时间为 7，B 在时刻 2 就第一次获得 CPU。

这三种顺序下，CPU 都从时刻 0 连续工作到时刻 10，在这个忽略开销的算例中利用率都是 100%，但平均周转时间分别是 9、6、7。

这个例子让我更容易区分：**CPU 是否忙碌、任务何时完成、任务多久能首次得到处理，是三个不同的问题。**

## 小结复盘 {#review}

这次我先记住调度的层次，再记住每种算法在看什么：FCFS 看到达顺序，SJF 看服务时间，SRTF 看剩余时间，HRRN 把已经等待的时间也考虑进去，RR 让大家按时间片轮流运行，MLFQ 再根据运行表现调整优先级。

它们并不是越往后就一定越好。批处理、交互和实时任务关心的目标不同，公平性、完成速度、响应和切换开销之间也会互相牵制。

回到具体题目时，我会先写清到达时刻、服务时间、时间片和队列规则，再画执行过程、计算指标。先看规则怎样改变任务的等待和执行，再去记算法的优缺点，会更容易把这些概念连起来。
